1-2주차에 정의한 핵심 문제는 **서버·인프라 모니터링 대응**이고, 5주차에 같은 "사람 개입 지연" 문제를 **PDF 활동지 수정 문의**에 적용하는 쪽으로 주제를 바꿨다. 두 기록을 함께 남긴다.

## 1. 핵심 문제 (1-2주차): 서버·인프라 모니터링 및 대응

### 한 줄 소개

Slack 알림 스레드에서 원인과 상황을 파악해 대응책을 제안하고, 사람이 고른 대응을 구현·테스트·PR까지 이어가는 모니터링 대응 에이전트

### 문제 정의

**장애 알림 분석과 대응이 사람 중심이라, 알림부터 릴리즈까지 최소 24시간이 걸린다.**

| | 내용 |
| --- | --- |
| AS-IS | Slack 알림 발생 → 코드 기반 skills로 디버깅 → 원인·대응 방안은 사람이 확인·결정 → 작업은 AI에 지시 → dev 테스트(목, 회귀 테스트 등) → prod 릴리즈 → 수동으로 추적 |
| 문제 근거 | 릴리즈·배포·검토에 절대적인 지연이 있고, 사람 개입으로 지연이 생긴다. 서비스마다 운영 시스템이 달라 유지보수가 어렵다 |
| 왜 이 방법인가 | 인력이 줄어 빠른 대응과 유지가 필요하다. 전 서비스가 AWS 기반이라 확인이 빠르고, 비슷한 상황끼리 분류할 수 있다 |

### TO-BE (단계)

1. Slack 알림 스레드로 원인·상황을 파악하고 대응책을 제안한다.
2. 사용자가 대응을 고르면 기록을 남기고, 구현·테스트·PR까지 진행한다.
3. 검증, 리뷰, 개선까지 이어간다.

1주차 피드백: 입력이 좀 더 정형화돼 있고, 긴급도(실시간성)와 중요도(사람 검토 필요 여부)로 나눠 볼 수 있으며, 일일 모니터링·메트릭 주기 감시로 접근할 수 있다.

### 해결 여부 확인 방법

| 결과 | 대응 시간 (Slack 알림 ~ 릴리즈) |

## 2. 5주차 주제 전환: PDF 활동지 수정 에이전트

### 한 줄 소개

비개발자가 고객 문의를 Slack에 올리면, 문의에 맞게 PDF 활동지를 수정하는 에이전트

### 막힌 점과 배운 점 (6주차)

- 고객 문의 케이스가 예상보다 다양해서 정확도가 낮다 → 이력과 책임을 분리해야 한다
- 회사에서는 Claude, 구현은 Codex를 쓰고 있어 도구가 나뉜다
- 사람 승인이 정말 필요한가 → 난이도에 따라 auto 모드를 둘지 검토 중
