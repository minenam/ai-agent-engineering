- 크루원: 우유진
- 개인 저장소:

## 한 줄 소개

Figma와 API 명세를 바탕으로 Android, iOS, 웹 기능을 구현하는 KMP 개발 에이전트.

## 문제 정의

**AI가 화면 구현을 끝냈다고 보고해도 디자인이나 요구사항이 빠지는 경우가 있음. 개발자가 빠진 부분을 다시 지시하고 수정 결과를 직접 확인해야 함.**

- 해결할 문제: 구현을 맡긴 뒤에도 누락 확인과 재검증을 개발자가 직접 해야 함.
- 목표: 보완 지시와 검증 기록 없는 완료 보고를 줄임.
- 가설: 요구사항과 디자인을 작업 및 테스트에 연결하고 검증 기록을 완료 조건으로 두면, 보완 지시와 검증 누락이 줄어들 것으로 봄.

### 해결 여부 확인 방법

| 지표 | 의미 |
| --- | --- |
| 사람 개입 횟수 | 보완 지시가 얼마나 줄었는가 |
| 자동 검증 통과율 | 실행한 자동 검증 중 통과한 비율 |
| 검증되지 않은 완료 보고 건수 | 근거 없이 완료라고 보고한 횟수 |
| 토큰 사용량 | 구현과 QA에서 쓴 토큰 수 |
| 요구사항 누락 수, 검토·수정 시간, 같은 문제의 재발 여부 | 1주차에 함께 제안한 지표 |

## 해결 방식

- 범위: KMP의 data, domain, ui 계층에서 목록과 상세 기능을 구현하고 검증함.
- 실행 흐름: 요구사항을 정리한 뒤 설계, 구현, 검증 순서로 진행함. 개발자 피드백은 다음 작업에 반영함.
- **실행 가드**: 코드 수정과 명령 실행 전에 승인된 작업, 단계, 기술 계약을 검사함. 작업을 끝낼 때는 검증 기록을 확인함.

## OpenAI 기술 활용

- Codex: `PreToolUse` 훅으로 코드 수정과 명령 실행 전 승인 범위를 확인함. `Stop` 훅으로 세션 종료 시 검증 기록을 확인함.

## 막힌 점과 배운 점

### 기술 합의와 실제 구현

역할별 실행 조건을 정하고 메모 앱을 만들어 봄. 공통 Compose UI는 의도대로 구현됐지만, 저장 방식은 에이전트가 확인 없이 로컬 DB로 정함.

기획, 디자인, 개발이 끝날 때마다 QA를 붙이고, 실패하면 오케스트레이터가 작업을 돌려보내도록 설계함. 플랫폼 지원 범위나 저장 방식이 애매하면 에이전트가 선택지를 제시하고 확인을 받도록 함.

### 실행 가드와 작업 재개

| 단계 | 내용 |
| --- | --- |
| 문제 | 기술 합의대로 작업하는지 실행 전에 확인하려고 가드를 붙인 뒤 작업 중 Git push와 에이전트 업데이트까지 막힘. |
| 원인 | 어떤 실행을 막을지는 정해 뒀는데, 작업이 멈췄을 때 기존 승인으로 이어가는 경로가 부족했음. |
| 대응 | 기획부터 독립 QA까지 이어서 실행하는 오케스트레이터를 추가했음. 작업이 끝나면 바꾼 내용과 이유, 검증 결과, 남은 문제를 적어 두도록 했음. v0.4.12에서는 기존 T2 승인을 다시 연결해 앱 구현을 이어갔음. |
| 후속 검증 | 웹 검증을 돌렸더니 시작 로그만 찍히고 테스트 프로세스는 뜨지 않음. v0.4.13과 v0.4.14에서 사전 검사와 잠금 대기 로그를 추가했음. 이후 데모 앱에서 다시 돌려 브라우저 검사 12개를 통과했음. |

Git push까지 막힌 뒤, 중단한 작업을 기존 승인으로 이어가는 경로도 필요하다는 걸 알게 됨.

### 지표 수집의 한계

- 토큰은 집계됐지만 구현, 검토, 수정 중 어디에 썼는지 알기 어려웠음. 실행을 시작할 때 작업 ID, 실행 ID, 역할, 목적을 함께 기록하도록 바꿈. 전체 진행 상황은 대시보드에, 현재 작업은 터미널에 표시함.
- 사용자 메시지에는 환경 지시와 QA 요청도 섞여 있었고, 토큰은 독립 QA 세션만 집계됐음. 이후 메시지를 유형별로 나누고 등록된 메인 구현 요청의 토큰을 추가함. 채팅 밖 승인과 미등록 구현 세션은 아직 빠져 있음.

## 앞으로 할 것

- 호환 Android 이미지에서 UI 테스트를 실행하고 네이티브 기기 간 서버 동기화와 토큰 보관소 동작을 확인함.
- 채팅 밖 승인 기록과 빠진 구현 세션의 토큰 사용량을 추가로 수집함.

## 차별점과 확장 계획

- 차별점: 구현을 마치면 독립 QA가 요구사항별로 결과를 확인함. 완료 조건에 필요한 테스트 기록이 빠져 있으면 완료 처리를 막음. 중단된 작업은 기존 승인을 유지한 채 같은 작업 시도에서 재개할 수 있음.
- 확장 계획: QA에서 발견한 문제마다 수정 내역과 재검증 결과를 함께 남김. 이후 같은 문제가 다시 나오면 이전에 어떤 수정으로 통과했는지 확인할 수 있도록 할 계획임.
