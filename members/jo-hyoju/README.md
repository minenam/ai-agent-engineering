## 한 줄 소개

사이드 프로젝트의 로그 분석, 코드 리뷰, 보안 점검, 문서 정리를 에이전트에 맡기되, 흩어지고 오래된 프로젝트 정보 대신 실제 코드 근거로 판단하게 만드는 미니 코딩 에이전트

## 문제 정의

**에이전트에게 로그 분석·코드 리뷰·보안 점검·문서 정리를 맡기려면 프로젝트를 이해하는 공통 기준이 먼저 필요하다.**

- 지금은 프로젝트 정보가 코드, README, 설정 파일, 컨벤션 문서 등에 흩어져 있고, 일부 문서는 현재 코드와 맞지 않는다.
- 이 상태로 에이전트가 작업하면 오래된 정보를 믿거나, 근거 없이 판단하거나, 민감정보를 잘못 다룰 위험이 있다.

### 해결 여부 확인 방법

- 로그 분석 시 민감정보를 노출하지 않는가
- 코드 리뷰 시 실제 코드 근거를 기반으로 판단하는가
- 보안 점검 시 추측이 아니라 확인된 사실을 기준으로 말하는가
- 문서와 코드가 다를 때 현재 코드를 우선하는가
- 다른 사람이 문서를 보고 같은 절차를 따라 할 수 있는가

## 해결 방식

| 주차 | 단계 | 산출물 |
| --- | --- | --- |
| 3주차 | 로그 분석 | 로그 수집·분석 절차, 분석 프롬프트, 장애 리포트 템플릿 |
| 4주차 | 코드 리뷰 | PR·변경 파일 리뷰 절차와 기준, 결과 포맷 |
| 5주차 | 보안 점검·모의해킹 대응 | 점검 시나리오, 취약점 분류 기준, 대응 리포트, 재점검 절차 |
| 6주차 | 문서 정리와 전체 흐름 통합 | 문서 갱신 절차, 통합 실행 가이드, 품질 평가, 데모 시나리오 |

### 보안 리뷰: 범용 리뷰와 같은 파이프라인, 다른 검증 기준

보안 리뷰를 별도 에이전트로 분리하지 않고, 같은 리뷰 파이프라인에 관점(angle)으로 추가하되 검증 기준만 바꿨다.

- 보안 리뷰는 기본으로 꺼져 있다. 모든 저장소에 보안 리뷰가 필요한 것은 아니기 때문이다.
- 대상 저장소의 `review.yaml`에 보안 관점을 명시하면 켜진다.

```yaml
security_angles:
  - authz           # 인증 누락 엔드포인트, 인가 검사 누락, IDOR, 권한 상승, 역할 검사 우회
  - injection       # SQL·커맨드·XSS·경로 조작·역직렬화·SSRF·템플릿 인젝션
  - data_exposure   # 시크릿 하드코딩, 민감정보 로깅·응답 노출, 취약한 암호화·해시·난수
```

| | 범용 리뷰 | 보안 리뷰 |
| --- | --- | --- |
| 판단 기준 | 지금 잘못 동작하는가 | 공격자가 악용할 수 있는가 |
| 검증 확인 항목 | 코드 근거 / 의도된 동작 / 실제 영향 | 도달 가능성 / 기존 방어 / 악용 영향 |
| 통과 기준 | `real` 2표 이상 (2/3 다수결) | 전원 합의 (3/3) |
| 주입 문서 | `AGENTS.md`, `REVIEW.md` | + `SECURITY-REVIEW.md` (보안 프롬프트만 봄) |
| 게시 상한 | 정렬 순서대로 자름 | 보안에 슬롯을 먼저 예약 |
| severity | important / nit / pre_existing | nit 금지 (보안 nit은 important로 올림) |

## 막힌 점과 배운 점 (6주차)

### 범용 리뷰 기준이 보안 취약점을 전부 걸러낸 문제

| 단계 | 내용 |
| --- | --- |
| 문제 | 범용 리뷰 에이전트의 검증 기준(항목)을 보안 리뷰에 그대로 썼더니, 취약점이 전부 탈락했다 |
| 원인 | 범용 리뷰의 "의도된 동작인가"는 좋은 오탐 필터다. 버그는 정의상 의도하지 않은 동작이기 때문이다. 보안은 반대다. 취약점은 거의 전부 의도적으로 작성됐고 지금 정상 동작하는 코드다 (보안에 취약할 뿐 동작은 정상) |
| 대응 | 보안을 별도 에이전트로 떼지 않고 같은 파이프라인에 관점으로 넣되, 검증 항목(도달 가능성 / 기존 방어 / 악용 영향)과 통과 기준(3/3 만장일치)을 따로 뒀다 |

탐지 프롬프트만 바꾸는 것으로는 부족하고, 검증 경로 전체를 관점에 맞게 바꿔야 한다.
